## Flynn v0.2.0

Since v0.1.3 a goal can be held to terms you write down, stopped from another terminal, and made to ask before it acts. Memory now knows which fact is current, what it was pushed and what it used. The binary includes thirteen skills, can show you what it knows, and can measure whether a skill helps. A command the agent runs now has no network unless you allow it (on Linux and macOS it cannot read your credentials either), and Flynn refuses a command it cannot confine instead of running it without a boundary. Every release from this one is rehearsed on each pull request, and the end-to-end suite runs against the release's own binaries on Linux, macOS and Windows.

Upgrading the binary: `flynn upgrade` from v0.1.3. Releases before v0.1.3 have no `upgrade` command; reinstall with the one-line script in the README, which verifies the archive's checksum. Read **Upgrading from v0.1.3** below first: the shell's defaults changed, a `flynn serve` channel now needs an allow-list, and the container image needs two security profiles to run commands. Importing the module: read **For hosts** as well; this release changes the memory interface a host implements.

### Upgrading from v0.1.3

- **Commands that fetch need `--allow-network`.** The shell has no network by default, so `git clone`, `git push`, package installs and anything else a command downloads fail until you pass it. Git over ssh with a key in `~/.ssh` also needs `--allow-credential-reads`; a deploy key kept outside the hidden locations is the narrower choice.
- **A served channel needs an allow-list.** `flynn serve` with a Telegram or Signal channel and no allow-list refuses to start. Add `--telegram-allow <user id>` or `--signal-allow <number>` (or `FLYNN_TELEGRAM_ALLOW` and `FLYNN_SIGNAL_ALLOW`, comma separated). Telegram senders are matched by numeric user id, not username, since a username can be changed or reassigned.
- **A host that cannot confine refuses commands.** v0.1.3 ran a command without a boundary where the sandbox was unavailable. This release refuses it. Ubuntu 24.04 and later restrict user namespaces through AppArmor, which is the common cause; `flynn sandbox check` names the cause on your host and the fix, and `deploy/apparmor/flynn` is the profile that lifts the restriction for the Flynn binary alone.
- **The container image runs commands, given its profiles.** The image now carries busybox on `gcr.io/distroless/static-debian13:debug-nonroot`, so the agent can run commands in it, which the v0.1.3 image could not. Docker's default seccomp and AppArmor profiles stop the sandbox from starting, so pass the two Flynn ships with each release (`flynn-seccomp.json`, and `flynn-apparmor-container` on an AppArmor host); `deploy/README.md` has the commands. Without them `flynn serve` and the API run as before and every command is refused with the cause. Do not use `seccomp=unconfined`, `apparmor=unconfined` or `CAP_SYS_ADMIN` instead.

### Testing a release candidate

The one-line install in the README fetches the latest final release, which is v0.1.3 until v0.2.0 is out. To install the candidate, set `FLYNN_PRERELEASE`:

- Linux and macOS: `curl -fsSL https://raw.githubusercontent.com/ionalpha/flynn/main/install.sh | FLYNN_PRERELEASE=1 sh`
- Windows (PowerShell): `$env:FLYNN_PRERELEASE = '1'; irm https://raw.githubusercontent.com/ionalpha/flynn/main/install.ps1 | iex`
- Already installed: `flynn upgrade --pre`

Run `flynn version` afterwards; it should name a `v0.2.0-rc` release. v0.1.3 cannot read a data directory the candidate has written and fails with `sqlite: no such column: uses`. If you keep the older binary, give it its own `--data-dir`.

### Goals you can govern

- **Terms of a run.** `flynn goal --goal-spec terms.json` states what must stay true while the run works, each with the command that checks it. Terms are checked after every step, before the goal is asked whether it is done, and a breach stops the run naming the term. Where the host's sandbox cannot contain a check, the run stops saying so rather than carrying on unchecked. `flynn help` shows the file's shape.
- **Approval.** `--require-approval <action>` pauses that action until a person authorizes it. The interactive session asks; a run with nobody to ask refuses the action. Every decision is recorded on the run's stream.
- **Irreversible actions.** `--irreversible <action>` marks an action as reaching outside the workspace for good; the run takes it only where `--allow <action>` (or the spec file's `allowances`) declared it. An undeclared one stops the run with the ask instead of handing the model a refusal to route around.
- **Kill and steer.** `flynn kill <run> "reason"` stops a running goal from another invocation; it takes hold on the run's next reconcile and refuses the next action. `flynn steer <run> "..."` redirects a run, which then cannot report success until it says what it did about the redirect.
- **Plans with proof.** A goal plans before it builds: the objective is expanded into an append-only ledger whose items each carry a check, and each check runs and is recorded. `--require-proof` stops a run from reporting success over an item its record cannot show a passing check for. A claim that something is absent needs the search that would have found it.
- **Runs that stop when they stop getting anywhere.** A run whose steps stop changing anything is stopped with a reason naming what it was last doing, rather than burning its whole step budget. A run that keeps pushing on one governance gate stops and says which rule refused it, and one that reached its objective through a refused gate settles as stalled, not converged. A goal can be bounded by tokens, cost and share of the plan window, with spend attributed per model tier.
- **Unit graphs (Go API).** A goal's spec can carry a declarative graph of units, run as governed child goals in dependency order, each admitted through the dispatch waist with its proof checked. From the CLI, `--fanout` lets the model delegate sub-goals itself.

### Memory

- **One current answer per subject.** A memory has a subject; a new fact on a subject supersedes the old one instead of sitting beside it. Memories carry an expiry and every source they came from.
- **Recall that ranks.** Recall scores relevance, filters by kind and time window, resolves scopes most-specific-first, and ranks by word match. Set `FLYNN_EMBED_MODEL` to an OpenAI-compatible embeddings model and it ranks by meaning as well, everywhere memory is read.
- **Push and pull, counted.** A run wakes with a digest of what this install knows, gated so that only memories you wrote or reviewed are pushed unasked. What the agent learned for itself waits for you: `flynn memory ls --pending` lists it with its sources, `flynn memory promote <id>` puts it in every later run's digest, and `revoke` takes it back out. A memory that came from untrusted input cannot be promoted, and that includes one learned in a run that used the shell or spawned a child, since Flynn cannot see what a command read or fetched (with `--allow-network` the shell can download anything). Until you promote it, a learned memory reaches a later run only through recall. Reading a skill also shows the run what earlier runs learned while using it. Every push and every use is recorded per instance; `flynn memory usage` reads it back, and an item pushed at readers who never use it is demoted.
- **Forgetting.** `flynn memory forget <id>` deletes a memory, including a fact pinned with `/remember`, which nothing later supersedes.
- **Consolidation.** `flynn memory consolidate` distils a subject's accumulated episodes into one lesson and retires them, with `--max-calls` capping the model spend.

### Skills

- **A bundled pack.** Thirteen engineering skills are built into the binary (systematic debugging, test-first, untrusted input, shared state, dependencies, deletion, and more), seeded into a scope nothing else can write to.
- **The Agent Skills format.** Flynn reads and writes `SKILL.md` skill directories, checked against the format's reference validator.
- **Offered, then read.** A run is offered skills by name and description and reads the body on request with `skill_read`. A skill is graded on the runs that read it, not the runs it happened to be shown to.
- **See and measure them.** `flynn skill ls` lists the pack and what this install learned, with reads and wins; `flynn skill show <skill>` prints one. `flynn skill ab <skill>` runs the skill's exercises with and without it, paired, and says whether it helped.

### What a command can reach

- **The shell is closed by default.** A command the agent runs has no network. On Linux and macOS it also cannot read the Flynn data directory, `~/.ssh`, `~/.aws` and the other cloud and CLI login tokens, or the keychain and agent sockets. `--allow-network` and `--allow-credential-reads` lift each separately, and every run records which it ran with as a `sandbox.posture` event before it starts. Windows cannot hide a path, so there the credential locations stay readable, Flynn prints a notice when a run starts, and the event records `"credentials_reason": "platform"`; `--require-credential-hiding` refuses to run commands instead. The same default covers `flynn goal`, `flynn serve`, the interactive session and the MCP server. `deploy/README.md` lists every hidden location.
- **No unconfined fallback.** Where the sandbox cannot confine a command, the command is refused with the cause and the fix. `flynn sandbox check [--json]` starts a real confined child and reports whether confinement works on this host and, if not, why. `deploy/systemd/flynn-runner.service` is a hardened unit for running Flynn as a service, and `deploy/apparmor/flynn` is the profile for Ubuntu 24.04 and later.
- **Served channels answer only who you list.** `flynn serve` drops a message from a sender not on the channel's allow-list before it is stored, so it never becomes a goal, and records the refusal (without the message text). A served goal now runs under the run flags you gave `serve` (`--require-approval`, `--allow`, resource limits) and charges its own budget, capped at your ceiling or 1,000,000 tokens when none is set.

### Verifiable record

- Signed checkpoints are COSE, and the Provetrail conformance vector suite is at version 0.1.0, generated here and verified by the reference verifier on every build.
- `flynn serve --api-issuer <key>` accepts capability tokens an operator issued under that key, so a remote operator can drive the box with a scoped, offline-verifiable token instead of a shared secret.

### Fixes

- `flynn goal --goal-spec f.json` and every other run flag written after `goal` were read as words of the objective, so the run went ahead without them. They are now read as flags, and one written after the objective is refused.
- `flynn serve` refused at start-up (an unsafe bind, nothing configured) left its heartbeat and service supervisor running against a closed store; it now stops them first.
- Stored timestamps sort in time order.
- A confined signer on Windows can read its sealed key.
- The interactive session could hang reading input when a multi-byte character arrived with no room left for it in the read buffer.
- Markdown in the terminal could render a line one cell wider than the screen, so it wrapped.
- An archive Flynn downloads and extracts (the local inference runtime, a command-line dependency) can no longer create a file named after a Windows device such as `NUL` or `COM1`.

### For hosts

`./dev/apidiff` against v0.1.3 reports these changes to the stable surface:

- `state.MemoryStore` has five new methods: `RecordPush`, `RecordUse` and `Usage` (the push and use record), `Promote` and `Promotions` (the review that lets an agent-written memory be pushed). Every host implementing the interface must add them. `storage/sqlite` is the reference implementation, and `memory/memorytest` is the conformance suite to run yours against.
- `state.MemoryItem.Source` is now `Sources []string`, alongside the new `Subject`, `Supersedes` and `ExpiresAt`.
- `state.Skill.Uses` is split into `Offers`, `Reads` and `Wins`. A record written before this release decodes its old count into `Offers`.
- `state.MemoryItem` and `state.RecallQuery` can no longer be compared with `==`.

Two changes the report cannot show:

- `sandbox.WithDefaultConfinement` now fails closed. Where the platform or host cannot confine a command, `Exec`, `Capture`, `Stream`, `Serve` and `Session` return a `RefusedError` naming the cause, where v0.1.3 ran the command unconfined. `WithBestEffortConfinement` is the explicit opt-in to the old floor, and it is recorded. `sandbox.CheckConfinement` is the same check `flynn sandbox check` runs.
- The conformance suites changed, so a backend that passed v0.1.3's suites may fail this release's. The files are listed under "Conformance suites changed" in the report.

The stable surface now also covers `resource`, `envelope`, `hlc`, `jobs` and `memory/memorytest`. `docs/VERSIONING.md` lists each port a host implements beside the suite that certifies it.

New importable packages, unstable while pre-1.0:

- `governed` composes a governed run the way the binary does, including the closed shell default (`WithShellPolicy` relaxes it, and the choice is recorded on the run's stream).
- `localmodel` provisions a digest-pinned llama.cpp runtime and catalog weights and serves them on loopback inside the sandbox; `flynn models` is now a client of it.
- `instance` publishes an instance's kind and heartbeat, and fails closed on liveness: a runner whose heartbeat is stale reads as unreachable.

The full exported-API report is at the end of these notes.

### Known limitations

- Windows cannot hide a path from a command the agent runs, so there the shell can read the data directory and the credential locations. Flynn prints a notice when a run starts and records `"credentials_reason": "platform"` on the run's `sandbox.posture` event. `--require-credential-hiding` refuses to run commands instead. Run Flynn inside a WSL2 distribution to have them hidden.

- On macOS the credential locations are hidden from the filesystem, but a command can still ask the keychain service for an item the account's keychain will hand out without a prompt.

- The container's command sandbox is tested under Docker on an AppArmor host. Podman, rootless Docker and gVisor are untested; `flynn sandbox check` in the container says whether confinement works there, and refuses rather than running commands unconfined.

- `--model claude` and `--model codex` refuse on native Windows. Both start the CLI through the same confined launch, which needs governed egress (the child's direct network denied, its traffic forced through Flynn's policy proxy), and Windows has no such enforcement yet. The refusal is `sandbox_egress_unsupported`; Flynn will not run the CLI with its network open. Run Flynn inside a WSL2 distribution to use either backend on a Windows machine.

### Release engineering

- Every pull request runs the release in snapshot form (all six targets, archives, deb/rpm/apk, SBOMs, container images) and the end-to-end suite against the release's own binaries on Linux, macOS and Windows, so a break in the release fails a pull request instead of a tag.
- Each release finishes by having the previous release's published binary upgrade itself to it with `flynn upgrade`, on each OS.
- The end-to-end suite now covers the learning loop, goal spec terms, approval, irreversible actions and `flynn kill` through the compiled binary.
- The Linux CI runners confine commands for real, and a runner that cannot confine fails the suite instead of skipping the confined tests.
- Each pull request runs `flynn sandbox check` in the release image three ways (Docker's defaults, the seccomp profile alone, both profiles): the first two must refuse and name the missing profile, the last must pass.
