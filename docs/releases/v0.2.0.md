## Flynn v0.2.0

Since v0.1.3 a goal can be held to terms you write down, stopped from another terminal, and made to ask before it acts. Memory now knows which fact is current, what it was pushed and what it used. The binary ships twelve skills, can show you what it knows, and can measure whether a skill helps. Every release from this one is rehearsed on each pull request, and the end-to-end suite runs against the release's own binaries on Linux, macOS and Windows.

Upgrading the binary: `flynn upgrade`. Importing the module: read **For hosts** below first; this release changes the memory interface a host implements.

### Goals you can govern

- **Terms of a run.** `flynn goal --goal-spec terms.json` states what must stay true while the run works, each with the command that checks it. Terms are checked after every step, before the goal is asked whether it is done, and a breach stops the run naming the term. Where the host's sandbox cannot contain a check, the run stops saying so rather than carrying on unchecked. `flynn help` shows the file's shape.
- **Approval.** `--require-approval <action>` pauses that action until a person authorizes it. The interactive session asks; a run with nobody to ask refuses the action. Every decision is recorded on the run's stream.
- **Irreversible actions.** `--irreversible <action>` marks an action as reaching outside the workspace for good; the run takes it only where `--allow <action>` (or the spec file's `allowances`) declared it. An undeclared one stops the run with the ask instead of handing the model a refusal to route around.
- **Kill and steer.** `flynn kill <run> "reason"` stops a running goal from another invocation; it takes hold on the run's next reconcile and refuses the next action. `flynn steer <run> "..."` redirects a run, which then cannot report success until it says what it did about the redirect.
- **Plans with proof.** A goal plans before it builds: the objective is expanded into an append-only ledger whose items each carry a check, and each check runs and is recorded. `--require-proof` stops a run from reporting success over an item its record cannot show a passing check for. A claim that something is absent needs the search that would have found it.
- **Runs that stop when they stop getting anywhere.** A run whose steps stop changing anything is stopped with a reason naming what it was last doing, rather than burning its whole step budget. A run that keeps pushing on one governance gate stops and says which rule refused it, and one that reached its objective through a refused gate settles as stalled, not converged. A goal can be bounded by tokens, cost and share of the plan window, with spend attributed per model tier.
- **Unit graphs (Go API).** A goal's spec can carry a declarative graph of units, run as governed child goals in dependency order, each admitted through the dispatch waist with its proof checked. From the CLI, `--fanout` lets the model delegate sub-goals itself.

### Memory

- **One current answer per subject.** A memory has a subject; a new fact on a subject supersedes the old one instead of sitting beside it. Memories carry an expiry and every source they came from.
- **Recall that ranks.** Recall scores relevance, filters by kind and time window, resolves scopes most-specific-first, and ranks by word match. Set `FLYNN_EMBED_MODEL` to an OpenAI-compatible embeddings model and it ranks by meaning as well, everywhere memory is read.
- **Push and pull, counted.** A run wakes with a digest of what this install knows, gated so that only operator-written or reviewed memories are pushed unasked. Reading a skill also shows the run what earlier runs learned while using it. Every push and every use is recorded per instance; `flynn memory usage` reads it back, and an item pushed at readers who never use it is demoted.
- **Consolidation.** `flynn memory consolidate` distils a subject's accumulated episodes into one lesson and retires them, with `--max-calls` capping the model spend.

### Skills

- **A bundled pack.** Twelve engineering skills ship in the binary (systematic debugging, test-first, untrusted input, dependencies, deletion, and more), seeded into a scope nothing else can write to.
- **The Agent Skills format.** Flynn reads and writes `SKILL.md` skill directories, checked against the format's reference validator.
- **Offered, then read.** A run is offered skills by name and description and reads the body on request with `skill_read`. A skill is graded on the runs that read it, not the runs it happened to be shown to.
- **See and measure them.** `flynn skill ls` lists the pack and what this install learned, with reads and wins; `flynn skill show <skill>` prints one. `flynn skill ab <skill>` runs the skill's exercises with and without it, paired, and says whether it helped.

### Verifiable record

- Signed checkpoints are COSE, and the Provetrail conformance vector suite is at version 0.1.0, generated here and verified by the reference verifier on every build.
- `flynn serve --api-issuer <key>` accepts capability tokens an operator issued under that key, so a remote operator can drive the box with a scoped, offline-verifiable token instead of a shared secret.

### Fixes

- `flynn goal --goal-spec f.json` and every other run flag written after `goal` were read as words of the objective, so the run went ahead without them. They are now read as flags, and one written after the objective is refused.
- `flynn serve` refused at start-up (an unsafe bind, nothing configured) left its heartbeat and service supervisor running against a closed store; it now stops them first.
- Stored timestamps sort in time order.
- A confined signer on Windows can read its sealed key.

### For hosts

`./dev/apidiff` against v0.1.3 reports these changes to the stable surface:

- `state.MemoryStore` has five new methods: `RecordPush`, `RecordUse` and `Usage` (the push and use record), `Promote` and `Promotions` (the review that lets an agent-written memory be pushed). Every host implementing the interface must add them. `storage/sqlite` is the reference implementation, and `memory/memorytest` is the conformance suite to run yours against.
- `state.MemoryItem.Source` is now `Sources []string`, alongside the new `Subject`, `Supersedes` and `ExpiresAt`.
- `state.Skill.Uses` is split into `Offers`, `Reads` and `Wins`. A record written before this release decodes its old count into `Offers`.

The full exported-API report is at the end of these notes.

### Release engineering

- Every pull request runs the release in snapshot form (all six targets, archives, deb/rpm/apk, SBOMs, container images) and the end-to-end suite against the release's own binaries on Linux, macOS and Windows, so a break in the release fails a pull request instead of a tag.
- The end-to-end suite now covers the learning loop, goal spec terms, approval, irreversible actions and `flynn kill` through the compiled binary.
